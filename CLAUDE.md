# CLAUDE.md

## Commands

```bash
# JS (admin/src/ → admin/build/, React 2.0 SPA)
npm run build      # wp-scripts build admin/src/index.js --output-path=admin/build
npm run start       # watch mode
npm run lint         # wp-scripts lint-js admin/src
npx wp-scripts lint-js admin/src --fix   # auto-fix prettier/eslint issues

# PHP
composer install            # dev toolchain (phpcs + phpunit)
composer install --no-dev   # production autoload (ships in the zip)
composer run phpcs          # WordPress Coding Standards lint
composer run phpcbf         # auto-fix what PHPCS can
composer run test:unit      # PHPUnit (WP_Mock, no DB)

# Inside a WordPress install (read-only; fails on any PHP notice from the plugin)
wp eval-file .github/ci/smoke.php
```

**PHP support: 7.4 and every later version, tested through 8.6.** `composer.json` pins `config.platform.php` to 7.4.33 so dev dependencies resolve to versions that run on every supported PHP (without it, an install on PHP 8.4 pulls packages that fatal on 7.4–8.2). `composer run phpcs` includes the `PHPCompatibilityWP` ruleset (`testVersion` 7.4-). `.github/workflows/php.yml` runs on every PR: PHPCS, then per PHP version (7.4–8.5 required, 8.6 non-blocking until its GA) a syntax check, PHPUnit and `.github/ci/smoke.php` in a real WordPress. When a new PHP version reaches GA, move it from `include` into the `php` list and add the next one as experimental. `ReflectionMethod::setAccessible()` is needed before 8.1 and deprecated from 8.5: guard it with `PHP_VERSION_ID < 80100`.

`vendor/autoload.php` + `vendor/composer/*` are committed as the **production (`--no-dev`) autoloader** — the zip, GitHub downloads and CI all load it. A local `composer install` rewrites them to reference dev packages (PHPUnit, Mockery, …) that `.gitignore`/`.distignore` exclude, and committing that version makes the plugin fatal on load (happened in 1.1.5 and again before 2.0.0). Locally these files are marked `git update-index --skip-worktree` so the dev versions never get staged; after a real dependency change, regenerate the no-dev autoloader in a temp copy, stage it with `--no-skip-worktree` toggled, and commit. Both the tag-deploy and Plugin Check workflows also run `composer install --no-dev` first — never remove those steps.

Always run `npm run lint` (fixing anything it flags) **and** `npm run build` after any change under `admin/src/` — the compiled `admin/build/` output is what actually ships and renders; editing `admin/src/` alone changes nothing live.

## Pre-commit gate

`.husky/pre-commit` (active — `git config core.hooksPath .husky`) blocks the commit on any failure of:

1. `npm run lint` — ESLint over `admin/src/`
2. `composer run phpcs` — WPCS, config in `phpcs.xml`
3. `composer run test:unit` — PHPUnit, config in `phpunit.xml`

Steps 2 and 3 are skipped when `vendor/bin/` is absent, so the hook still works on a checkout with no dev toolchain installed — run `composer install` to get the real gate.

The whole codebase is currently PHPCS-clean, so **any** new violation is yours; fix it rather than widening the ruleset. Where a sniff is a genuine false positive (a `$wpdb` table name interpolated from `$this->table_name`, a nonce already checked in `validate_nonce()`), the codebase uses a narrowly-scoped `phpcs:ignore`/`phpcs:disable` with a `--` reason appended. Match that pattern; never blanket-disable a sniff in `phpcs.xml`.

**`composer install` note:** `10up/wp_mock` is hosted under the `10up` GitHub org. A fine-grained GitHub PAT that doesn't include that org makes Composer fail with `Could not authenticate against github.com` — the package is public, so `COMPOSER_HOME=$(mktemp -d) composer install` (no token) is the quick workaround; the real fix is re-scoping the PAT.

## Architecture

- Main plugin class: `Nhrotm_Options_Table_Manager` (prefix `Nhrotm_`, namespace `Nhrotm\OptionsTableManager\`, PSR-4 → `includes/`).
- REST namespace: `nhrotm/v1` (routes: `nhrotm/v1/dashboard`, `nhrotm/v1/dashboard/activity`, `nhrotm/v1/dashboard/activity/{id}/restore`, `nhrotm/v1/browse`, `nhrotm/v1/browse/lookup`, `nhrotm/v1/browse/save`, `nhrotm/v1/browse/bulk-delete`, `nhrotm/v1/browse/{id}`, `nhrotm/v1/cleanup` + `/preview` + `/run` + `/schedules`, `nhrotm/v1/option-history?name=` (per-option versions for Browse → History; deliberately not under `/browse/` so it can't shadow `/browse/{id}` for a transient named "history"), `nhrotm/v1/optimize` + `/disable-autoload` + `/delete-orphans` + `/reset-usage` + `/clean-transients` + `/tables` + `/tables/action`, `nhrotm/v1/tools/backups*`, `nhrotm/v1/tools/search-replace` + `/count`, `nhrotm/v1/tools/cron` + `/run` + `/delete`, `nhrotm/v1/tools/export` (`names[]` = selected only) + `/export/search`, `nhrotm/v1/tools/import` (`selected[]`) + `/import/preview`, `nhrotm/v1/integrations` + `/{slug}` (`search`, `orderby`, `order`), `nhrotm/v1/settings` + `/prune-history` + `/history-stats`; multisite only, gated on `manage_network_options`: `nhrotm/v1/network/sites`, `/network/options`, `/network/options/{id}`, `/network/clean-transients`).
- **Abilities (AI agents, MCP)** — `Core\Abilities`, WordPress 6.9+ (the two `wp_abilities_api_*` hooks never fire before that, and only fire when something asks for the registry, so the front end pays nothing). Twelve `nhrotm/*` abilities in the `nhrotm` category: read-only `get-health`, `list-cleanup-types`, `preview-cleanup`, `get-autoload-report`, `list-tables`, `list-cron-events`, `search-options`, `list-activity`; writes `run-cleanup` (`dry_run` defaults to true), `disable-option-autoload`, `optimize-table`, `create-snapshot`. Each is a thin wrapper over a service, gated by `Abilities::can_manage()` (`manage_options`), and flagged `public` + `show_in_rest` + `mcp.public` so the WordPress MCP Adapter (not bundled) exposes it. Rules: **no ability returns an option or meta value** (whatever it returns goes to the agent's AI provider; `search-options` strips `preview`, `list-cron-events` strips `args`), and **nothing irreversible beyond a cleanup** (no table empty/drop, Search & Replace, import, single-option edit/delete, cron delete, settings). Core validates the output against `output_schema`, so keep schemas loose (`object`/`array`) unless the shape is guaranteed. Adding or changing an ability means updating `tests/AbilitiesTest.php` (pins the exact list and annotations), the readme FAQ and `.ai/PRD.md` §4.3.
- **Name:** the plugin is "NHR Database Cleaner & Optimizer – Revisions, Transients, Autoload & Options Manager" (header and readme title must match exactly); the UI says "Database Cleaner" (never "NHR"). The slug, text domain, `nhrotm` prefix and REST namespace are unchanged and must stay so. The WP-CLI command is `wp nhrotm` (since 2.1.0); `wp nhr-options` is registered as an alias for pre-2.1 scripts and must keep working.
- **Cleanup** (`CleanupService`): every type is one `spec()` entry — literal SQL fragments (table/join, WHERE, pk, label, date column) plus a delete strategy. Posts and comments are deleted through core (`wp_delete_post_revision()`, `wp_delete_post()`, `wp_delete_comment()`); meta, term relationships and Action Scheduler rows are deleted directly by id in batches of 200 within a 15-second budget (meta deletes clear only the meta cache of the objects they touched; never `wp_cache_flush()` here, a scheduled cleanup would empty the whole object cache), and the UI/CLI keep calling until `remaining` is 0. Request values only ever select a type id and a number of days; they never reach SQL text. Schedules live in `nhrotm_settings['cleanup_schedules']`, one `nhrotm_cleanup` cron event per type (arg = type id); `duplicate_*` and `orphan_post_types` are manual-only. User-meta types are hidden on multisite except for network user managers on the main site.
- **Tables** (`TablesService`): a table name reaches SQL only after an exact match against `SHOW TABLE STATUS`. Core is a hard-coded list (plugins add their own tables to `$wpdb->tables`, so that property can't be trusted to mean "core"). Empty/Drop only for `leftover`/`unknown` owners, and only with the name typed.
- **Cron** (`CronService`): an event is addressed by hook + timestamp + args signature and looked up in the cron array; the request never supplies a hook or arguments to execute. Core hooks can be run, never deleted. "Possibly orphaned" is only a hint — many plugins attach cron callbacks only during cron requests.
- **Network** (`NetworkService`, multisite): `wp_sitemeta` browse + delete (core keys in `PROTECTED_KEYS` refused), per-site figures. Its page is Network Admin → Settings → Database Cleaner (`AppPage::register_network_menu()`), which boots the same bundle with `boot.network` and a single `network` module.
- **Snapshots never contain or restore the `cron` option**; `ToolsService::restore_backup()` re-runs `SettingsService::migrate()` and `CleanupService::sync_cron()` afterwards.
- **No tables, ever.** The plugin creates no database tables and must never add one (`CREATE TABLE`/`dbDelta` are banned here and in the add-on; decided 2026-10-04). Recorded data goes in non-autoloaded options with a hard cap. Before 2.1 there were two tables, `nhrotm_option_history` and `nhrotm_option_backups`; `HistoryManager::upgrade()` / `BackupManager::upgrade()` copy their newest rows into options and drop them, and `uninstall.php` still drops them for sites that never ran that step.
- **Data migrations:** `Nhrotm_Options_Table_Manager::DB_VERSION` + `maybe_upgrade_db()` (runs on activation and on the first **admin, cron or WP-CLI** request after an update, never on a visitor's page load; the `nhrotm_migrating` option is an `add_option()` lock so two requests can't migrate at once, taken over after 10 minutes; the version is stored inside `nhrotm_settings`). Bump the constant and add a step whenever a stored shape changes. Steps must be resumable: `BackupManager::upgrade()` deletes each old row as soon as it is stored. `DB_VERSION` matches the plugin version that introduced the shape (currently `2.1.0`).
- **Nothing runs on the front end.** `Core\Bootstrap` builds the module list (and the one `SHOW TABLES` query Integrations needs) only on `rest_api_init` and `admin_menu`; `init_plugin()` must stay at zero queries for a visitor request. Usage tracking (opt-in) records every load up to 200, then 1 in 10 counted as 10 (`UsageTracker::SAMPLE_AFTER` / `SAMPLE_RATE`), and stops at 10,000.
- **History** (`HistoryManager`) is one option, `nhrotm_history` = `[ 'next' => id, 'rows' => [ id => row ] ]`, capped at 300 rows and 1 MB of values (oldest dropped first); a value over 100 KB is logged without its content (`value_dropped`) and is not restorable. Each `log_change()` rewrites the option. Rows carry `record_type`; only `options` rows are restorable (`HistoryManager::is_restorable()`). When logging a meta `update`/`create`, pass the type to `ActivityService::record()` — the action alone can't tell option from meta.
- **Snapshots** (`BackupManager`) are an index option `nhrotm_snapshots` plus one payload option `nhrotm_snapshot_{id}` each (max 15), storing `gz:` + base64(gzcompress(json)); `decode()` still reads legacy plain-JSON payloads. They exclude transients, `cron` and the plugin's own data options. Scheduled snapshots are skipped when the `checksum` matches the latest one.
- **Bulk actions and the history log:** every `log_change()` rewrites the whole `nhrotm_history` option, so a loop that logs per row wraps itself in `HistoryManager::defer()` … `HistoryManager::flush()` (one write; see `BrowseService::bulk_delete()`).
- **Search & Replace** handles every match (names first, then one value at a time), skips protected options in both the count and the run, and clears the option cache for each row it rewrites.
- **The plugin's own data options** (`BackupManager::data_options()` / `is_data_option()`: `nhrotm_history`, `nhrotm_snapshots`, `nhrotm_snapshot_*`) are appended to `get_protected_options()` (no edit, delete or import), and are left out of snapshots, Export all and Search & Replace. Any new feature that walks every option must skip them too.
- **Allow HTML in option values** (`allow_html_in_values`, default off) is applied in `BrowseService::apply_html_setting()` to the Options type only, and only for users with `unfiltered_html` (`BrowseService::can_store_html()`; WP-CLI counts as trusted). A user without that capability (site admin on multisite, `DISALLOW_UNFILTERED_HTML`) always gets HTML stripped, for meta values too, and `ToolsController` refuses Import and a live Search & Replace with 403, because both write raw values. Off strips HTML from plain values and from every string leaf of JSON/serialized values; keys, numbers and booleans are never altered (the 1.x Classic sanitizer ran `sanitize_key()` on array keys and silently renamed them — don't port that back).
- **Import** (`ToolsService::parse_import()`) accepts both the 2.x export format (`option_name`/`option_value`) and the 1.x/Classic one (`name`/`value`); a `checksum` over `options`, when present, must match.
- **Integrations** sort by column *position* (`ORDER BY n`) resolved by comparing the request against `SHOW COLUMNS` output, and search with one prepared `LIKE %s` per schema column — no request value ever reaches the SQL text.
- **Settings** live only in `nhrotm_settings` (`SettingsService`), one **autoloaded** option that also carries the data version under the internal `db_version` key (`db_version()` / `set_db_version()`; `all()` never returns it and `update()` cannot change it). The front-end usage tracker reads its on/off switch straight from this option (`UsageTracker::enabled()`), so there is no separate flag option. Keep it small: it loads on every request, so never put growing data in it. Never read legacy `nhrotm_*` setting keys — `migrate()` deletes them (including the pre-2.1 `nhrotm_db_version` and `nhrotm_usage_tracking_enabled`).
- **Option budget:** the plugin's whole footprint is four fixed options — `nhrotm_settings` (autoloaded), `nhrotm_usage` (tracker data: `since`, `loads`, `used`), `nhrotm_history`, `nhrotm_snapshots` — plus one `nhrotm_snapshot_{id}` per snapshot (max 15). Don't add a new option for a new feature; extend one of these.
- Browse covers six record types: `options`, `usermeta`, `postmeta`, `commentmeta`, `termmeta`, `transients` — same CRUD + protected-key pattern across all of them (`BrowseService`).
- Usermeta/postmeta tabs have a "filter by user/post" search-as-you-type combobox (`admin/src/components/IdLookupFilter.js`) that resolves a typed name/title to an id via `GET nhrotm/v1/browse/lookup?target=post|user&search=`; the actual grid filter is always a plain `WHERE user_id = %d` / `WHERE post_id = %d` in `BrowseService::query_usermeta()`/`query_postmeta()` — the combobox exists only so a user isn't expected to know that id.
- **Add-on API** (consumed by the private add-on `nhrrob-options-table-manager-pro`, which gates on `NHROTM_VERSION`; there is no separate API-level constant): PHP filters `nhrotm_modules`, `nhrotm_app_boot`, `nhrotm_health_recommendations`, `nhrotm_activity_describe`; action `nhrotm_app_enqueued`; JS `window.nhrotm` (shared components, `useToast`, `useConfirm`, `registerIcons`) + the `nhrotm.screens` filter. Changing any of these is a breaking change for the add-on — keep the old hook working, or ship the free release first and raise the add-on's `MIN_CORE_VERSION`; update `.ai/PRD.md` §3. **The free codebase never mentions PRO**: no Pro tags, Upgrade screen, upgrade URL, `hasPro`/`proAvailable` boot keys or "PRO" in comments or strings (removed 2026-10-04, PRD §1.2). Say "add-on" in code comments.
- Admin React SPA (`@wordpress/scripts`, no CSS framework, hand-rolled components) mounts at `#nhrotm-app` on `Tools → Database Cleaner`. Source in `admin/src/`, compiled output in `admin/build/` (the only thing actually enqueued — `AppPage.php::enqueue()` reads `admin/build/index.asset.php` for the content-hash version, so cache-busting is automatic on every build; a stale-looking browser is almost never a caching bug, verify against a fresh build before assuming so).
- CSS: single hand-authored `admin/src/style.scss`, all custom properties (`--nhrotm-*`) scoped under `.nhrotm-app`. See **§14.4 below** — anything rendered outside that DOM subtree loses every token silently.
- `includes/Services/BrowseService.php` queries `wp_options`/`wp_usermeta` directly (prepared statements, whitelisted `ORDER BY` via `resolve_order()`). Note: `wp_options` has **no timestamp column** — `option_id`/`umeta_id` (auto-increment) is the only available proxy for "creation order," used for the default newest-first sort.

## UI implementation preferences (read before touching admin/src/ or style.scss)

This is the condensed, load-bearing checklist distilled from a full UI/UX polish pass. Full rationale, code-level detail, and the specific bugs each rule was born from: **`.ai/DESIGN.md` §14** (`UI implementation gotchas`) — read that section in full before making non-trivial CSS changes; this is the quick-reference version.

1. **Component consistency is non-negotiable.** Same button height/padding/radius/shape as existing `.nhrotm-btn`/`.nhrotm-iconbtn`/`.nhrotm-segmented__item` siblings — never introduce one-off pixel values for a "new" button. Every clickable element gets an explicit `:hover`. No exceptions — this has been audited and fixed once already app-wide.
2. **Every native form control (`input`, `textarea`, `select`, checkboxes, `a`) needs an explicit `:focus` override, and it must reset `outline`, `border-color`, *and* `box-shadow` together.** wp-admin core sets real styles on these elements (not just resets) — including a themed `box-shadow` ring — and winning the cascade for one property (e.g. `outline`) does nothing for the others core also sets. Half-fixing this is the single most repeated bug this session. See DESIGN.md §14.1.
3. **Focus convention: focus gets the same darkened border as hover.** `:hover { border-color: var(--nhrotm-text-muted); }`, `:focus { border-color: var(--nhrotm-text-muted); outline: none; box-shadow: none; }` — still no `box-shadow` ring, but focus is no longer visually indistinguishable from resting state. Reverted 2026-09-21 (user request) from an earlier "focus changes nothing" convention — don't revert this again without checking with the user first.
4. **Checkboxes: never use `accent-color`.** Fully custom-drawn (`appearance: none` + `clip-path` checkmark) — `accent-color` checkboxes get a native focus halo Chrome paints that no CSS can suppress. Also explicitly reset `min-width: 0` (wp-admin sets `min-width: 1rem` with no matching `min-height`, which silently produces a non-square box) alongside the usual `outline`/`box-shadow` reset. See DESIGN.md §14.2 — this exact rule has regressed twice already from an incomplete rewrite.
5. **`.nhrotm-btn` variants need a real, visible `border-color` — never rely on the transparent base border.** A shadow alone (e.g. on hover) blends into a similarly-toned fill with nothing to anchor the button's shape.
6. **CSS custom properties (`--nhrotm-*`) only resolve inside `.nhrotm-app`'s DOM subtree.** Any provider/portal that renders UI (modals, toasts, tooltips) must be mounted as a *descendant* of `<AppShell>` (nest it under `children`), never as a wrapper around `<AppShell>` — a wrapper renders as a DOM *sibling* of `.nhrotm-app` and silently loses every token (fully transparent modal, no error). See DESIGN.md §14.4.
7. **Success feedback → `useToast()` (fixed, auto-dismissing, non-layout-shifting).** Never an inline notice that shifts the toolbar. Wording: **"X successfully."**
8. **Destructive/irreversible actions → `useConfirm()`.** Never `window.confirm`. Always pass a `description` (either a natural second sentence, or "This action cannot be undone." for plain deletes) — a confirm dialog with only a title reads as unfinished.
9. **Tables:** bold (`700`) headers, normal-weight (`400`) body content including name/key columns, zebra-striped rows (`nth-child(even)`, `--nhrotm-bg`) with a stronger `:hover` tint layered on top. Row actions are icon + text label, never icon-only.
10. **If a screen has default sort/filter state, check every code path that can reset it** (tab switches, type changes, not just the initial `useState`) — this regressed once when a tab-switch handler reset sort to a different default than the one on mount.
11. **A toolbar/header row's line count must never depend on whether its content happens to fit.** If different tabs/states render different amounts of toolbar content (Browse: some types have 0 extra filters, some 1, Transients has 2), letting `flex-wrap` decide per case means each type wraps at a different width, so the grid header sits at a different height per tab and switching tabs "jumps." Force a fixed row count instead (Browse's `.nhrotm-browse__tools` now carries `flex-basis: 100%` so it's always its own row on every type). See DESIGN.md §14.8 — this bit us once already via the loading-skeleton row count (`typeRowCountRef`) and came back in a new form when the Usermeta/Postmeta id-lookup filter was added.
12. **Sharing a CSS class doesn't guarantee two controls look the same — check the wrapper too.** `JumpNav`'s quick-jump pill and Browse's type switcher both use `.nhrotm-segmented`, but `JumpNav` used to sit inside its own boxed strip (`.nhrotm-jumpnav`'s background/border/padding) while Browse's sits bare — same pill, two visibly different "tab bar" treatments. See DESIGN.md §14.10.
13. **A panel with much less content than its siblings needs its own layout, not just left-aligned text in a full-width body.** Optimize's Cleanup panel (description + count + one button) left the whole right half of the panel blank next to Autoload health/Orphan scanner's full-width tables — fixed by reusing the existing `.nhrotm-card` component (same one Dashboard uses) as a stat tile beside the description, not inventing a new one. See DESIGN.md §14.11.
14. **`table-layout: fixed` (the `.nhrotm-grid` default) needs an explicit `<colgroup>` of `nhrotm-col-*` widths.** A table whose columns aren't known ahead of time — e.g. Integrations, whose columns come straight from a third-party plugin's own DB schema — has no `<colgroup>` to give it, so the browser squeezes an arbitrary number of columns into the container's fixed width and their `nowrap` header text overflows on top of the neighbouring column instead of wrapping or scrolling. Give that table the `.nhrotm-grid--fluid` modifier (`table-layout: auto`) instead, so it sizes to its content and `.nhrotm-grid__scroll`'s `overflow-x: auto` can actually scroll it. See DESIGN.md §14.12.
15. **Under `table-layout: fixed`, add up the fixed `nhrotm-col-*` widths before reusing them in a new table — the flexible `nhrotm-col-name` column only gets what's left, and that can be 0.** The content panel is ~930px wide on a typical laptop. Optimize → Tables shipped with seven columns and 924px of fixed widths, so the table name wrapped one letter per line and Owner drew on top of it. Fix: the storage engine is shown as a muted line under the table name instead of in its own column (still searchable), and a per-table modifier passed through `DataTable`'s `tableClassName` prop (`.nhrotm-grid--tables`) sets the remaining five fixed columns to 706px with a 910px `min-width`. Size the Actions column for two buttons side by side (232px) and let more wrap. Also never leave an Actions cell blank — when no action applies, say so ("Nothing to do"). See DESIGN.md §14.13.

## Security invariants (WP.org automated release review blocks high-risk findings)

- Every REST route: `permission_callback => [ $this, 'can_manage' ]` (`manage_options`); routes are also only registered for users who pass the module capability. The plugin registers no `wp_ajax_*` handlers (the Classic UI's were removed in 2.1); if one is ever added it needs a nonce **and** `current_user_can( 'manage_options' )` — a nonce alone is not authorization.
- **Multisite:** user meta is network-wide. Usermeta Browse + user lookup require `manage_network_users` (`BrowseController::can_manage()` checks `type=usermeta` / `target=user` on every Browse route). Protect user meta with `is_protected_usermeta()`, never `in_array( …, get_protected_usermetas() )` alone — it matches every site's `{base_prefix}{id}_capabilities|user_level|…`. The roles option is protected under its real name (`{prefix}user_roles`). On the main site the Tables list includes network-wide tables, so `TablesService::can_act()` requires `manage_network` there for every table action. Trait constants are PHP 8.2+, so shared lists in `GlobalTrait` are methods. Per-site lifecycle: network activation runs `activate_plugin()` for the main site only, so every site sets itself up lazily (`maybe_upgrade_db()` per site option, `ensure_crons()` on admin/cron requests); deactivation (`$network_wide`) and `uninstall.php` loop `get_sites()`. Verify on a throwaway subdirectory network (`~/Sites/otm-ms`; simulate a subsite cron request with `wp --url=otm-ms.test/two --require=<file defining DOING_CRON> eval ''`, WP-CLI with `--url=otm-ms.test/two`; Valet can't route subsite wp-admin, so browser checks run on the main site with a non-super-admin administrator).
- **Destructive database actions** (cleanup, table empty/drop, cron delete, network option delete) must keep their server-side guards — the UI's confirm is not the protection. Unit tests in `tests/SafetyRulesTest.php` pin them.
- Never call `unserialize()`/`maybe_unserialize()` on option data without `allowed_classes` — `false` for pass-through (restore), `[ 'stdClass' ]` only where objects must be walked (Search & Replace). Imports reject serialized non-stdClass objects via `GlobalTrait::is_unsafe_import_value()` and skip protected core options.
- Every ability: `permission_callback => [ $this, 'can_manage' ]`, same gate as REST.
- Automated in `.github/workflows/security.yml` (every PR to main): Semgrep `p/php`, PHPStan (`.github/security/phpstan.neon`, level 0 + WordPress stubs), and `.github/security/probe.py` + `endpoint-probe.php`: discovers every plugin-owned AJAX action/REST route/ability, forces nonces valid, calls each as subscriber and anonymous (for an ability: its permission check), and fails on any success response or attempted DB write (writes are blocked). See the release skill's Step 0.5 for running it locally.
- Build `ORDER BY` from literals/whitelist comparisons, never from the request value (even validated) — Semgrep's taint analysis flags `$columns[ intval( $_GET[...] ) ]`. Prepare each query exactly once; never embed an already-prepared fragment in another `prepare()`.
